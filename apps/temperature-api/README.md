## Задание 1.Анализ и планирование

### 1.1.Анализ функциональности существующего монолита

#### — Управление отоплением

* Пользователи могут удаленно управлять отоплением в доме: включать и выключать.
* Система поддерживает запросы к системе управления отоплентем в конкретном доме.
* Система поддерживает только включение и выключение отопления.

#### - Мониторинг температуры в доме

* Пользователи могут проверять температуру в помещении по датчикам, которые установила компания.
* Пользователи могут просматривать температуру в веб-интерфейсе.
* Система поддерживает запросы к датчикам для мониторинга температуры.
* Датчики могут присылать уведомления о регистрации при включении.

### 2. Анализ архитектуры монолитного приложения

* Система представляет собой монолит, написанный на языке Go.
* В качестве СУБД используется PostgreSQL.
* Обработка вызовов от датчиков происходит синхронно, в одном процессе.
* Горизонтальное масштабирование не предусмотренно.

**Язык программирования:** Go<br>
**База данных:** PostgreSQL<br>
**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.<br>
**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.<br>
**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.<br>
**Развертывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

> **Домен:** Управление умным домом.

>> **Поддомен:** Мониторинг температуры.
>>> **Контекст:** Запрос температуры у датчика.<br>
>>> **Контекст:** Сохранение данных о датчике в системе.<br>
>>> **Контекст:** Вывод температуры пользователю по запросу.<br>

>> **Поддомен:** Управление отоплением <br>
>>>**Контекст**: Включение/отключение отопления пользователем <br>
>>>**Контекст**: Включение/выключение отопления системой (передает запрос от пользователя на конкретное устройство) <br>
>>>**Контекст**: Включение температуры пользователем <br>

>> **Поддомен:** Обработка профилей пользователей и устройств
>>> **Контекст:** Регистрация пользователя
>>> **Контекст:** Регистрация датчика
>>> **Контекст:** Регистрация системы отопления

### 4.Проблемы монолитного решения
1. Масштабирование.
> 1. Синхронные последовательные запросы не позволят использовать вертикальное масштабирование.
> 2. При горизонтальном масштабировании будут дублироваться компоненты, которые не испытывают сильной нагрузки.
2. Расширение имеющейся функциональности:
> 1. Добавление новых датчиков и систем требует обновления кода монолита.
> 2. Возможны ошибки и отказы системы при добавлении новой функциональности.
3. Развертывание
> 1. Требуется остановка приложения для развертывания, что может вызвать недовольство пользователей, пока сервис будет недоступен.
4. СУБД
> 1. PostgreSQL кажется излишним, можно воспользоваться NoSQL решением.
